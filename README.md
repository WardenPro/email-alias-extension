# Email Alias Extension (Chromium + Firefox)

MV3 extension for Chromium and Firefox to generate random aliases for your own domain and use Cloudflare Email Routing so aliases forward to your personal mailbox.

## Features

- Alias format: `site-slug-random@yourdomain.tld`
- Site-aware slug from current tab (ex: `amazon-abc123@...`)
- Main action: **Generate + Create + Copy**
- Optional action: fill detected email input on current page
- Local alias history (extension local storage)
- Cloudflare API integration:
  - ensure destination address exists
  - ensure catch-all rule forwards to destination email

## Requirements

- Cloudflare Email Routing enabled on your domain
- A Cloudflare API token with minimal scopes for Email Routing and zone read/edit as needed
- Chromium/Chrome in developer mode, and/or Firefox 128+ (`about:debugging`), for unpacked extensions

## Setup

1. Install dependencies:
   ```bash
   npm install
   ```
2. Build both targets (or one of them):
   ```bash
   npm run build
   npm run build:chrome
   npm run build:firefox
   ```
3. Load the unpacked extension:
   - Chromium/Chrome: `chrome://extensions` (Developer mode) -> **Load unpacked** -> `dist/chrome`
   - Firefox: `about:debugging#/runtime/this-firefox` -> **Load Temporary Add-on** -> `dist/firefox/manifest.json`
   - Firefox only: the first save or **Test Cloudflare API** in the options page asks permission for
     `api.cloudflare.com`. Grant it, otherwise alias creation fails (Firefox MV3 host permissions are opt-in).
4. Open extension options and set:
   - Domain (ex: `example.com`)
   - Forward destination email (your personal inbox)
   - Cloudflare Account ID
   - Cloudflare Zone ID
   - Cloudflare API token
5. Use popup button **Generate + Create + Copy**.

## Bitwarden workflow

1. Open signup page.
2. Click extension icon.
3. Click **Generate + Create + Copy**.
4. Paste alias in email field.
5. Save credentials in Bitwarden.

## Releases and CI

The build/test job runs on every push and pull request. The jobs that publish
anything are restricted to this fork via `github.repository_owner == 'WardenPro'`,
so no release is ever created and nothing is pushed to a store from another
repository:

- `release` — attaches both zips (`-chrome`, `-firefox`) to the `latest`
  release on `main`, and to the tag release on `v*`.
- `publish-webstore` — uploads the Chrome zip on `v*` tags, and is skipped with
  a log line (instead of failing) when the `CWS_*` secrets are not configured.

Firefox/AMO submission stays manual.

## Browser targets

Both builds share the same sources; only the manifest differs (generated by
[`manifest.config.ts`](manifest.config.ts)):

| | Chrome | Firefox |
| --- | --- | --- |
| background | `service_worker` | `scripts` (module event page) |
| min version | `minimum_chrome_version: 114` | `strict_min_version: 128.0` |
| extension id | Web Store assigned | `browser_specific_settings.gecko.id` |
| host permission | granted at install | user opt-in, requested from the options page |

Extension APIs are accessed through the `ext` namespace in
[`src/lib/browser.ts`](src/lib/browser.ts) (`browser` when available, else `chrome`).
